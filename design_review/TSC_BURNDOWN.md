## TIER 1 — money, units, provenance, facts gateway · **43 errors · ALL FIXED**

### 1. `frontend/lib/buildCashFlowStatement.ts` — 17 errors · FIXED

**What a user would see:** a money cell in the Cash Flow statement rendering
a concatenated string, and the statement's own reconciliation guarantee
silently no longer being checked.

`assembled_cf` is genuinely heterogeneous — real engine output carries
`is_approximated` and `dividends_declared_but_unpaid` (bool) and
`approximation_notes` (`string[]`) in the same record as ~30 numeric keys.
Every read was a bare `?? 0`, typing as `number | boolean | string[]`, and JS
coerces rather than throws. Measured, not asserted:

```
cfBeforeWcChanges   = "Working-capital movements estimated3695525.59"  (string)
cashUsedInInvesting = false
wcReconciliationPlug = NaN     →  the ">50k" disclosure note never fires
drift = NaN                    →  "balances within RON 1" evaluates NaN, silently
```

**Fix:** `cfNum()` narrows at the read — the one place a downstream caller
cannot forget. Non-finite treated as absent (one NaN poisons every derived
total identically).
**Test:** `frontend/lib/__tests__/cashFlowNumericNarrowing.test.ts` — 15 tests.
Verified non-vacuous: **7 fail** against pre-fix behaviour.

### 2. `frontend/lib/publicCompanyAdapters.ts` — 14 errors · FIXED

**What a user would see:** on the public-company Balance Sheet, "Total equity
and liabilities" showing equity alone — for AAPL FY2024 the balance check was
off by **$308bn** — and "Total non-current liabilities" rendering *negative*.
On the Cash Flow tab, investing and financing sections showing `0.00` beside
`isApproximated: false` and `drift: 0`: a fabricated clean reconciliation.
Every liquidity ratio `computeRatios` derives (current, quick, debt-to-assets)
was inflated, because current liabilities were understated by the whole
non-debt stack.

The adapter read `headline.total_liabilities`, `.investing_cash_flow`,
`.financing_cash_flow`. **Verified against the real engine:** `normalizer.py`
builds the headline dict from exactly ten keys and none of those three are
among them — though all three exist on `adapter.Fundamentals`. Absent → `?? 0`
→ rendered as fact.

**Fix — two remedies, because the cases differ:**
- `total_liabilities` **is** recoverable: derived by the identity A − E, exact
  to the dollar against the filed figure (364,980 − 56,950 = 308,030).
- CFI/CFF are **not** recoverable (no identity reaches them; the only
  cash-flow leaf emitted is `cash_operating`). They now return `null`, the
  sections are withheld, and the statement flags itself approximated with a
  disclosure note — rather than printing a zero.

**Test:** `frontend/lib/__tests__/publicCompanyAbsentNotZero.test.ts` — 11
tests over a fixture generated by the real `normalizer.normalize()`.
Verified non-vacuous: **8 fail** against pre-fix behaviour.

> **CROSS-LANE — engine, one line:** forward the three fields that already
> exist on `Fundamentals` into the `headline` dict in
> `src/engine/public/normalizer.py:226`. That restores real CFI/CFF instead
> of a disclosure, and makes the identity-derivation redundant. Not done
> here: engine source is another lane's, and §14 deploy protocol applies.

### 3. `frontend/lib/periodFacts.ts` — 7 errors · FIXED

**What a user would see:** a served-facts value silently reverting to a
locally-computed approximation, permanently, with nothing raised.

`bsField(k: keyof BSFacts, …)` named the **wrong vocabulary**. It indexes the
engine's `assembled_bs` key space, which is a different vocabulary from the
FE-facing `BSFacts`: `ar_intercompany` vs `intercompany_loans`, `ap` vs
`suppliers`, `total_debt` vs `bank_debt_total`. It typechecked only for the
handful of names spelled the same in both — and it actively invited the bug:
passing a real `BSFacts` key compiles clean and then misses on every lookup.
**Verified against real engine output:** none of `intercompany_loans`,
`investment_property_net`, `suppliers`, `dividends_payable`,
`bank_debt_total` exists in `assembled_bs`.

**Fix:** a `CanonicalBsKey` union naming the engine's real key space, so a
miss is a compile error. Plus `PeriodValuation` gained `asset_based_equity`
and `equity_ebitda_p50` — both genuinely emitted by `_valuation.py`, read
through a type error while building the valuation fact block.

### 4. `frontend/lib/buildPlStatement.ts` (6) + `buildBsStatement.ts` (6) · FIXED

**What a user would see:** a P&L or BS row rendered at the wrong visual
weight — an item silently typed as a `subtotal` reads as a total — or a
wrong `sign`, which drives the ± prefix on a money amount.

`const x: PLLine[] = [ … ].filter(f)` annotates the **filter result**, never
the array literal. Uncontextualised, `style: "item"` widens from `LineStyle`
to `string`, `sign`/`bucket` stop being checked at all, and the predicate is
then rejected outright (TS2677).

**Fix:** `plLines()` / `bsLines()` — the literal is passed as an *argument*,
which restores contextual typing. No cast; every field is checked again.

### 5. `frontend/pages/cfo/Products.tsx` — FX provenance · FIXED

**What a user would see:** every converted CSV export shipping
`# FX provider: n/a · rate date: n/a` — the exact disclosure the exporting
function's own comment says *"No converted CSV ships without."*

`ratesPayload.rateDate` / `.provider` do not exist on `RatesPayload`; the
fields are `as_of` and `source`. Both reads were `undefined`. The rate itself
was always correct — only its provenance was missing, which is the harder
half to notice in a file handed to a bank or an auditor.

### 6. `frontend/lib/publicCompanyIntelligence.ts` + `RiskRadar.tsx` + `CompanyExposureDetail.tsx` — 6 errors · FIXED

**What a user would see:** an AI-inferred exposure score wearing the
provenance badge of a modelled one, and a real 10-K extraction downgraded to
"sector" — from the badge whose only job is to keep those apart. The engine's
own comment: *"so the LLM prompt can refuse to present inferred numbers as
verified facts."*

`ExposureSource` was declared **twice in one file** with different member
sets (TS2300). The second — `"sec_filing" | "operator_curated" |
"bvb_override"` — is a fiction: **those strings appear nowhere in the
engine.** The real vocabulary is `filings | sector_model | ai_inferred |
manual`. Both badge tables were keyed on the fiction, so 3 of the 4 real
values missed the lookup and fell through `?? "sector"`. Only `sector_model`
ever matched. The file's claim that the type gives it exhaustiveness was
destroyed by the duplicate — and is now true again.

### 7. `frontend/lib/learning/buildReportingMetrics.ts` · FIXED

**What a user would see:** the entire "Cash Flow" category in the learning
surface with no numbers, and a scenario capex lever that cannot move
anything.

`statements.cashFlow` does not exist on `Statements` — it never has. All
seven cash-flow metrics were permanently `undefined`. `CascadeState` **is**
`ReportingMetrics`, so the scenario engine was adjusting `num(undefined) === 0`.

**Fix:** read the canonical `assembled_cf` — the same view the Cash Flow tab
renders — *not* `deriveCashFlow()`, which is an approximation
(`cfo = NI + D&A − ΔWC`) and would have put a second, disagreeing cash-flow
number on a different screen. Sign convention verified against real output
rather than assumed: `CFO + CFI + CFF = net_change_in_cash` holds exactly,
which is the identity the `net_change_in_cash` concept declares.
**Test:** `frontend/lib/__tests__/reportingMetricsCashFlow.test.ts` — 10 tests.

### 8. `frontend/lib/scenarios/cascade.ts` + `types.ts` · FIXED

**What a user would see:** every "where did this number come from" drill-down
on a scenario's output silently broken, with the metric reported as 0.

`conceptKey: keyof ReportingMetrics` admits `accountTraces` — a
`Record<string, AccountTrace[]>`, the source-trace map — and
`applySingleAdjustment` writes `{ ...state, [conceptKey]: <number> }`.
Nothing constructs that target today; the type simply permitted it.

**Fix:** `AdjustableMetricKey`, a mapped-type filter over the numeric members.
Verified by probe: `conceptKey: "accountTraces"` is now `TS2322`,
`"revenue"` still compiles.

### 9. `TraceableNumber.tsx`, `PLStatementView.tsx`, `PublicCompanyDashboard.tsx` · FIXED

- **TraceableNumber** — `rates: Record<string, number>` admits a table
  missing a currency; `convertFromTo` reads by key, so a missing RON converts
  against `undefined` and puts a wrong figure under a correct-looking
  currency label. Narrowed to `Rates`; the one call site already passes one.
- **PLStatementView** — `LineSign` has three members, the money formatter's
  `sign` option has two. `"neutral"` fell through to the formatter's default,
  which happens to be right — load-bearing **by accident**. Mapping made
  explicit; rendered string byte-identical.
- **PublicCompanyDashboard** — `ev_ebit` / `ev_revenue` are emitted by
  `normalizer.py` beside `ev_ebitda`, but were missing from the interface, so
  two valuation-multiple tiles were typed as though the data could not exist.

## TIER 2 — real correctness risk elsewhere · **41 errors · ALL FIXED**

### The systemic one: `strict: false` breaks else-branch narrowing

**Found three times, independently.** With `strict: false` (hence
`strictNullChecks: false`), TypeScript will **not** subtract the `ok: true`
member from a boolean-discriminated union in the negative branch. Measured
directly — the identical snippet compiles clean under `--strict true` and
reports TS2339 under `--strict false`. The call sites are correct at runtime;
the compiler mode is the artefact.

| Site | Errors | Status |
|---|---|---|
| `publicCompanyApi.ts` `ApiResult` → Dashboard, SearchPage | 2 | FIXED — `isApiError()` predicate |
| `marketApi.ts` `MarketCompanyResult` → refusal tests | 6 | FIXED — `isMarketRefusal()` predicate |
| `capsuleAskGuard.ts` `CapsuleAskDecision` | **10** | **LANE D — see handover** |

A user-defined type predicate narrows under both modes, compiles to a plain
`!r.ok`, and suppresses nothing: a genuinely wrong access still fails.

## Remaining 10 — handover to lane D

`frontend/components/instrument/shell/capsuleEmpty/` — the Capsule tree,
being measured live by lane D. **Not touched, by instruction.**

All ten are one root cause: the `strict: false` narrowing artefact above.
`capsuleAskGuard.ts:188` `decision.allowed ? 0 : decision.retryAt` and
`:208-209` after the `if (decision.allowed) return` early exit; the test file
inherits the same 7 times. The fix is the same four lines already applied
twice in this pass:

```ts
export function isCapsuleAskBlocked(
  d: CapsuleAskDecision,
): d is Extract<CapsuleAskDecision, { allowed: false }> {
  return !d.allowed;
}
```

Then `if (isCapsuleAskBlocked(decision))` at the three call sites and the
seven in the test. Runtime behaviour is unchanged — it compiles to `!d.allowed`.
**One PR clears the board to zero.**
