# F3.16-3b.5 — Canonical envelope backfill design

**Status:** Design (read-only probe complete; execution authorised next session)
**Author:** Engineering
**Date:** 2026-05-25
**Prerequisite for:** 3b.5 step 2 (F3.15 fallback deletion), 3b.6 (F4.2 consumer cutover)

## Why this backfill exists

Direct prod query (`scripts/probe_backfill_classify.py` run via
`docker exec cfo-ai-backend`) reveals that **8 of 9** prod
`financial_periods` rows have `assembled_canonical_v1 = NULL`. These
periods are read today via the F3.15 legacy fallback (re-derives
canonical-shape values from the persisted statements). The fallback
is correct enough for the FE to render, but it masks the underlying
storage gap and blocks 3b.6's F4.2 consumer cutover (which assumes
every analyzed period has an envelope persisted).

3b.2's Path X kwarg + the pack-wrapper fix produced **1 period with a
fresh envelope** (`a64a682e-87b2-4aa6-b3ef-b30dee6b7df7`, RealEstate
re-triggered as part of post-deploy verification). The other 8 stay
on the legacy fallback until backfilled.

## Why re-assemble doesn't work for this set

The Path X fix makes the kwarg available to `assemble_statements`,
but the kwarg value (`statutory_net_profit_anchor`) is COMPUTED FROM
RAW TB ROWS during `stage_extract`. The line_items table stores the
mapped-bucket output — raw 121 rows were never persisted. Re-running
`assemble_statements(persisted_line_items, account_121_anchor_override=NULL)`
yields the same output as today (with the F3.15 fallback masking it).

**Only re-running stage_extract from the source xlsx/pdf provides
the raw rows needed to compute the anchor.** Hence re-extract is the
forced strategy.

## Backfill execution plan

### Phase 0 — snapshot (rollback safety)

Before any backfill writes, snapshot each period's current state into a new
`pre_backfill_snapshot` JSONB column on `financial_periods`. Migration:

```sql
ALTER TABLE financial_periods
  ADD COLUMN IF NOT EXISTS pre_backfill_snapshot JSONB;

UPDATE financial_periods
SET pre_backfill_snapshot = jsonb_build_object(
  'snapshot_at', now(),
  'snapshot_version', 'F3.16-3b5-v1',
  'assembled_canonical_v1', assembled_canonical_v1,
  'updated_at', updated_at,
  'methodology_version', methodology_version,
  'detection_envelope', detection_envelope
)
WHERE pre_backfill_snapshot IS NULL
  AND id IN (
    '5feafe69-...', '6c6b8503-...', 'd30954df-...', '57f52f21-...',
    '377e43be-...', '92788026-...', '158a5746-...', 'b50cbdb2-...'
  );
```

Rollback: if any backfilled period's user-visible numbers (computed
from re-derived canonical envelope) differ from the pre-backfill
F3.15-fallback values by > 0.5% on `total_assets` or > 5% on
`current_year_pnl`, REVERT that period's `assembled_canonical_v1` to
`NULL` and re-flag it as `manual_review_required`. Standard discipline
allows operator to either accept the new values or re-investigate.

### Phase 1 — execute in 2 batches of 4 periods each

8 periods / 4-per-batch = 2 batches. Each batch:

1. Run `_run_pipeline_sync(doc_id)` for each of 4 docs (in series; no
   need to parallelize for 8 total)
2. Wait for `documents.status = 'analyzed'`
3. Verify `assembled_canonical_v1` is now populated + `round_trip_check.passed = True`
4. Compare new `total_assets` and `current_year_pnl` against
   pre-backfill snapshot; flag if delta > tolerance
5. Run **F-A3.1** between batches — must stay GREEN; halt-and-diagnose
   if any calibrated fixture moves

Expected wall-clock: ~48s per period × 4 = ~3.5 min per batch + F-A3.1
check (~10s) = ~4 min per batch. Total: ~8 min for the full backfill.

### Phase 2 — F-A3.3-ENVELOPE-COVERAGE gate

New gate added in the same PR as the backfill execution, captured as
follow-up work:

**Spec for `scripts/measure_envelope_coverage.py`:**

- Query every `financial_periods` row where `status = 'analyzed'`
- For each: assert `assembled_canonical_v1 IS NOT NULL` AND
  `assembled_canonical_v1->>'schema_version' = 'canonical_v1.0.0'` AND
  `(assembled_canonical_v1->'round_trip_check'->>'passed')::bool = TRUE`
- Any row failing any assertion is **RED**; total RED count > 0 fails the gate
- Threshold widening explicitly forbidden — mirrors F-A3.1's discipline
- **Prerequisite for 3b.6's F3.15 fallback deletion.** F3.15 fallback
  cannot be removed until F-A3.3 is GREEN on every period across every
  organization

### Phase 3 — F3.15 fallback deletion (separate PR, separate day)

Per the original 3b.5 discipline: deletion is irreversible and goes in
its own PR. The backfill (phases 0-2) is reversible via the
`pre_backfill_snapshot` column. Only after every period in the DB
has an envelope and F-A3.3 is GREEN does the F3.15 fallback get
deleted — replaced with a hard error so future canonical-envelope
gaps surface immediately instead of silently routing through the
legacy fallback.

## Rollback decision tree

| Trigger | Action |
|---|---|
| F-A3.1 RED on any calibrated fixture after batch | HALT batch sequence. Diagnose which fixture moved. Revert batch's pre_backfill_snapshots. |
| Single period's `total_assets` delta > 0.5% from pre-snapshot | Revert THAT period only. Flag for manual review. Continue batch. |
| Single period's `current_year_pnl` delta > 5% from pre-snapshot | Revert THAT period only. Flag for manual review. Continue batch. |
| Single period's `round_trip_check.passed = False` post-backfill | Revert THAT period. Investigate before next batch. |
| Pipeline error on `_run_pipeline_sync(doc_id)` | Skip period (no snapshot consumed). Investigate xlsx/pdf integrity. |

## Open questions surfaced by the probe

1. **Why do EEI/Sibiu PDFs land only 60-200 line_items?** Scandia
   xlsx produces 644-653; PDFs should land in a similar range if the
   PDF TB parser ran cleanly. Possibly the PDFs hit Claude fallback
   and Claude over-summarized. Worth checking
   `documents.extraction_method` (currently NULL on all 8 — column
   may not be populated).
2. **Does the re-extract produce different line_items than today?**
   If yes, downstream consumers (briefings, alerts, recommendations)
   may re-fire. Plan: run one period through phase 1 manually, diff
   the line_items pre/post, decide whether downstream re-firing is
   acceptable.
3. **Multi-period org behavior.** Some orgs may have 2-3 periods.
   Backfilling one period in isolation could create cross-period
   inconsistency in the briefing (e.g., "FY2025 grew 12% vs FY2024"
   computed from old FY2024 + new FY2025). Plan: backfill periods
   within the same org in chronological order, latest last.
