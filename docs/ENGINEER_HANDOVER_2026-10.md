## 1. What the product is

**CFO AI** (cfo-ai.io) turns a Romanian company's trial balance (balanță de verificare — an
xlsx or a PDF export from SAGA / WinMentor) into a CFO-grade analysis: the three statements,
some 25 ratios with industry bands, a credit score (Altman Z″, Piotroski, a composite letter),
a valuation envelope, risks and ranked recommendations, an AI-written briefing, and an
"Ask CFO AI" chat grounded in the company's numbers (CLAUDE.md §1–§3, Appendix A). A public,
indexable storefront serves summary pages for ~600k Romanian legal entities from open filings
(§21). Accounting firms over many client companies ("Firm Cockpit") exist in code but are hidden
in production.

The engine's one rule, repeated through every section of CLAUDE.md: **a figure that cannot be
computed is refused and says why — it is never 0, never a placeholder, and never computed in
the browser.** Every user-visible number comes from the Python engine; the frontend prints.

### The four pieces

| piece | what it is | where |
|---|---|---|
| **Engine** | Python / FastAPI (`src/engine`, ~560 files; the import graph is drawn in `docs/engine_book/architecture.md`, regenerated by `scripts/generate_engine_book.py`). Parses the book, classifies accounts through country packs (`src/engine/country_packs/ro_romania`), assembles statements, ratios, credit, valuation, narrates with the model, serves `GET /api/period/{id}`. Runs as ONE Docker container `cfo-ai-backend` on one VPS (`/opt/cfo-ai`, `docker compose`), fronted by Caddy (`scandia-caddy`, §21) | `src/engine`, `packs/`, `scripts/` |
| **Frontend** | Vite SPA (React, TypeScript, i18n EN/RO), built into an nginx container `cfo-ai-frontend` (§19). `frontend/lib/cfoApi.ts` is the single chokepoint to the engine; `lib/money` the single number printer (§26) | `frontend/` |
| **Supabase** | auth (e-mail + Google), Postgres with row-level security (workspace == organization, `is_member_of(org_id)` on every org-scoped table, §16), the `documents` storage bucket, and two Edge Functions: `chat-llm` (the chat generation, §16 Milestone D / §32) and `fx-rates` (BNR exchange rates, §30). The engine talks to Postgres through PostgREST with the service-role key (`src/engine/api/_supabase.py`) | `supabase/` — see `supabase/MIGRATION_ORDER.md` |
| **Model + money** | the Anthropic API (two keys — section 4) and Stripe (`_billing.py`, webhooks) | `src/engine/api/_billing.py`, `_usage_gate.py`, `_plan_state.py`, `_pricing_config.py` |

### The discipline: batteries, gates, plants

Nothing ships on "tests pass". The project runs a **battery** — `scripts/run_battery.py` — of
~175 gates in canonical order; each gate declares a **WORK count** (what it examined, read back
from its own output) with a **FLOOR**, and a **CANARY** literal it must print. Exit 0 with work
below the floor is a FAIL; a missing canary is "DISCOVERY BROKEN". The reason is in the script's
docstring: `npx tsc --noEmit` sat green for months while checking zero files.

Every gate has a section in **`docs/engine_book/gates.md`** (the gate register;
`tests/engine/test_gate_canaries.py` reds when a gate has none). A section records the
**plant**: a defect deliberately inserted, the exact RED output the gate produced, and the
revert that put it back GREEN. "Plant / red / revert" is how a gate earns the right to exist —
a gate that was never seen red proves nothing (§23 TC-11: "state what it fails on AFTER the
defect is repaired"; memory note *gates-that-encode-the-defect*). Independent adversarial
reviews precede every engine, money, auth or customer-data change; frontend-only display fixes
skip the review but not the gates (§33, owner's rule).

## 3. How to deploy

### 3.1 Backend and frontend (CLAUDE.md §14, in a newcomer's words)

The host's source tree at `/opt/cfo-ai/src` is the truth; the running container is built from
it. The sequence, which `specs-durable/deploy_lane.sh <worktree> <label> <prod_base_commit>`
automates (`FE=0` / `BE=0` skip a side; `ALLOW_MOVES=1` only for a deliberate number change):

0. **Anchors + served baseline.** Take the lock (`mkdir /tmp/cfo-ai-deploy.lock`; released on
   exit — a lane killed with -9 leaves it: read `holder`, confirm nothing runs, `rmdir`). Tag
   both running images `:rollback-<label>`. Dump every stored period's served verdict with
   `check_served_periods.py --dump` (the DATA gate — a vacuous pass is RED).
1. **Full-tree sync + verify.** `git ls-files` over `src scripts packs frontend corpus
   methodology config.yaml pyproject.toml requirements-lock.txt` plus the frontend image's other
   inputs, sha256 on both sides, rsync only what differs, verify 0 mismatched; remove on the host
   the files the range deletes. Never rsync several files with differing basenames into one
   directory (§14 rsync discipline — a `pipeline.py` once clobbered another `pipeline.py`).
   SQL files in the range are printed and NOT shipped: they are applied by hand (3.2).
2. **Build** — `docker compose build backend frontend` on the host.
3. **Pre-flight in the NEW image, before anything is switched:** an import/wiring probe
   (`PREFLIGHT_PY`); `check_served_periods.py` through `docker compose run --rm --no-deps` and a
   diff against step 0 (0 verdicts may move); `check_fresh_upload.py` (a real trial balance
   through all five stages); then the **boot probe** — `docker run` the new image with the
   real `.env`, poll `/health`, remove it (a pack the image cannot read crash-loops after the
   switch; this catches it first). Any failure here retags the anchors and never touches the
   running containers.
4. **Switch** — `docker compose up -d --force-recreate <services>`; wait for `healthy` and the
   site's 200; otherwise automatic rollback to the anchors.
5. **Post-deploy gates:** F-A3.1 `measure_bs_drift.py` (both fixtures GREEN), `check_fresh_upload.py`
   again, `check_served_periods.py` again and diffed against step 0, the container's file hashes
   against the commit's, the live bundle name. Since r-trust also `check_fx_live.py` +
   `check_fx_served.py` (§30), `check_deploy_drift.py` (IN SYNC) and `check_deployed_routes.py`;
   since r-share `check_served_periods.py --require-common-size` in the pre-flight (§37). From this
   release, read the staged rows first
   (`select id, org_id from financial_periods where source_document_id is null and
   assembled_canonical_v1 ? 'staged_rerun'`) — a row there is a re-run in flight, not a moved
   verdict (ticket T90).

Then write the ops_log line: commit, both image ids, the bundle name, the anchors, what the
gates read. One deploy at a time, always; whoever deploys second merges the other's commit first.
A frontend-only deploy leaves `scripts/run_battery.py` on the host one commit newer than the
container's copy — a dev script, carried by the next backend build (T67).

### 3.2 A migration (the two-step protocol, §14)

1. Run the file: `supabase db query --linked -f supabase/<file>.sql` (the Management API runs it
   as `postgres` in one batch and returns the LAST statement's row — every 2026-10 file ends with
   a jsonb row saying what it did), or paste it in Supabase Studio. Run its read-only report
   BEFORE (`hole_open` / `verdict`) and AFTER (closed / `fully_locked`); the fingerprints must be
   equal.
2. **Immediately click Dashboard → Settings → API → "Reload schema cache"** for anything that
   adds or changes a column or table. The `NOTIFY pgrst` in the file is optimistic on Supabase's
   managed PostgREST; the click is the deterministic step. Verify through REST
   (`GET /rest/v1/<table>?select=<column>&limit=1` → 200), not `pg_catalog`. An orchestrator that
   writes a new column calls `verify_pgrst_visibility()` first. If the column still 400s after
   NOTIFY + the click + toggling an API setting: stop, open a Supabase ticket (§14).

A migration that adds a column the backend writes goes in BEFORE that backend is switched
(`briefing_stale`, the two `ebitda_definition` files). The order of every file and the re-run
traps are in `supabase/MIGRATION_ORDER.md`.

### 3.3 An Edge Function (§16 Milestone D, §30, §32)

```
# what is deployed today, into a SCRATCH dir, and diff it against the checkout
supabase functions download chat-llm --project-ref cjclenykwlngqvapmisb --use-api --workdir <scratch>
diff -ru <scratch>/supabase/functions/chat-llm supabase/functions/chat-llm
supabase secrets list --project-ref cjclenykwlngqvapmisb          # names only
supabase db query --linked -f supabase/preflight/chat_cap_always_preflight_report.sql   # ready: true
supabase functions deploy chat-llm --project-ref cjclenykwlngqvapmisb --use-api --no-verify-jwt
supabase functions deploy fx-rates --project-ref cjclenykwlngqvapmisb --use-api --no-verify-jwt
```

After a `chat-llm` deploy: a second download must show the four files; zero-cost live checks —
OPTIONS from the site → 200; POST with no bearer → `401 sign_in_required`; POST with the public
anon key → 401; from a signed-in browser, `{"messages": []}` → `400 invalid_request` (the bearer
verified inside the function, nothing reserved). A real message is a billed call — the owner's to
send. Rollback = redeploy the previous source. `--no-verify-jwt` is deliberate: the function
verifies the bearer itself so its 401 carries a typed body and it answers the CORS preflight.

### 3.4 Three things that are never done

1. **No `docker cp` of engine code into a running container** (§14). The F1.f/F1.g additions
   were hot-patched that way, the next `docker compose build` read the host source and silently
   dropped them for weeks. Host source first, then rebuild — no exceptions, including one-line fixes.
2. **No Pydantic model defined inside a router factory** in a module with
   `from __future__ import annotations` (§22). `ToolCall` and `ContactSalesRequest` were: every
   Capsule tool call and every contact-sales submission answered 422 in production, and
   `/openapi.json` 500'd. Module scope, always; gate `route-binding` makes the nested shape red.
3. **No lazy `import()` on an error path** (§24). `lib/uploadRefusals` was imported only on the
   non-OK branch, so it was its own content-hashed chunk; a tab older than the last deploy 404'd it
   exactly when the server answered 402, and "Analysis failed" replaced the dashboard for a document
   the server went on to analyse. Static import; a persisted terminal state never replaces a surface.

Two more rules worth the same weight: never run `PUBLIC_TEST_MODE` against production (8,498 junk
workspaces once; memory note *test-mode-junk-workspaces*), and never `set role anon|authenticated`
in a `postgres` session of a local Supabase Postgres and then call a function that role may not
execute — on image 17.6.1.106 it segfaults the server (§31).
