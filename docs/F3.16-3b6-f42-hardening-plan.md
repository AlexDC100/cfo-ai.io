## ⚠️ Prediction Correction — logged 2026-05-26 (revised mid-session)

**Original plan §8 predicted all 8 fixtures at ±0.00 RON
post-cash-hardening after removing an SBC (share-based compensation)
strip from the YAML `cash` formula. Empirical F4.2-PARITY run
revealed the prediction was wrong on the cash variant; a second
pre-deploy probe revealed the prediction was ALSO wrong on the
strict variant (which the plan treated as already byte-identical).**

### Cash variant — predicted ±0.00, empirical 100-1571 %

- **(a) RO RAS doesn't have SBC accounting.** OMFP 1802 has no
  share-based-compensation account class. The "SBC strip" the
  original plan blamed for the divergence does not exist in the
  Romanian chart of accounts — the line item was a phantom carried
  over from a US-GAAP mental model. Removing it from the YAML would
  have been a no-op.

- **(b) The actual cash divergence comes from a different
  strip-set mismatch.** The YAML `cash` formula subtracts revenue
  reversals (`722`, `711`, `781`) and `fx_gain`, then adds back
  `provision_charges`, `fx_loss`, and `impairment_receivables`.
  The in-code path computes a bare EBITDA (operating result + D&A)
  with none of those adjustments. Empirically this produces
  **100-1571 % divergence** across the 8 fixtures — none of which
  is fixable by deleting a non-existent SBC line.

### Strict variant — predicted ±0.00, empirical 16K – 3.23M RON

- **(c) The pre-3b.6-A gate never actually checked strict.** §1 of
  this plan claimed `strict` was "already HARD ±1 RON" alongside
  `reported`. Reading the gate code in

### Lesson, recorded here so future contributors hit it first

**Methodology-layer predictions require reading both the YAML AND
the in-code formula AND the gate code itself before locking the
prediction.** The gate's behavior is part of the system under
prediction — claiming "strict is already HARD" is a claim about
the gate, not just about the YAML. The F3.16 ADR's "predict before
deploy, validate after" discipline (invariant b) is only as good
as the prior the predictor brought to the prediction; if any of
the three artifacts (YAML formula, in-code formula, gate behavior)
is left unread, the prediction is unfounded.

If you can't write down all three side-by-side before predicting,
your prediction is unfounded — write `±?` instead of `±0.00` and
explicitly flag the variant as unanalyzed.

This is the same pattern as the F3.16 ADR's wrap around the
121-anchor comment: wrong predictions stay as historical evidence
with explicit "what went wrong + why" framing, not silent
overwrites. A future contributor hitting "but the doc said
±0.00 RON cash" or "but the doc said strict was already HARD"
needs to see this correction first, then the follow-up ticket
trail, before they spend a session re-discovering why the
original predictions were wrong.

The §1 table below (and §8 "what ships" punch list) is preserved
**unchanged** so the original mispredicts stay visible. Read the
§1 cash row as "what the original plan thought, before reading
the formulas." Read the §1 strict row as "what the original plan
thought, before reading the gate code." Read this correction
block as "what the formulas + gate code actually said."

**Same class of save as Path X** — the disciplined unwind of an
over-scoped original plan into a properly-sized ship is itself
a sprint win, not a setback. The cost of catching this at deploy
time is one session of revised plan doc + one bundled follow-up
ticket. The cost of NOT catching it would have been a RED F4.2
gate on 7 of 8 fixtures, an operator scramble, and a much messier
unwind.

## What this plan ships

Three coupled changes — gate, consumers, briefing prompt — that together
make `methodology.ebitda.reported` the **single source of truth** for
every EBITDA value the product surfaces. Today most consumers read
in-code legacy fields (`assembled_pl.ebitda_statutory` and friends) and
the methodology YAML's `ebitda.cash` variant is allowed to diverge from
the in-code `ebitda_cash` value as "info only." After 3b.6:

- F4.2-PARITY gate is HARD on all four EBITDA variants (no info-only).
- Every UI consumer reads canonical methodology fields, with feature
  flags so individual surfaces can revert if cutover breaks them.
- Briefing prompt explicitly forbids the LLM from computing new EBITDA
  values in prose (fixes the Carniprod −6.87M briefing-prose problem).

This is the last RO-pack architectural-debt item before F3.16 closes.

## §1 — F4.2-PARITY gate hardening spec

### Current behavior (post-3b.2)

`scripts/check_methodology_parity.py` (the F4.2-PARITY gate) compares
four EBITDA computations per fixture:

| Variant | YAML field | In-code field | Current gate behavior |
|---|---|---|---|
| Reported | `methodology.ebitda.reported` | `assembled_pl.ebitda_statutory` | **HARD** (≤ 1 RON delta) |
| Strict   | `methodology.ebitda.strict`   | `assembled_pl.adjusted_ebitda`  | **HARD** (≤ 1 RON delta) |
| Cash     | `methodology.ebitda.cash`     | `assembled_pl.ebitda_cash`      | **info only** (5% threshold, doesn't fail gate) |
| Adjusted | not yet computed in YAML      | `assembled_pl.adjusted_ebitda`  | not yet gated |

The "info only" loophole on `cash` was added during F4.2's initial
calibration because the YAML's cash variant strips a different set of
non-cash items than the in-code path (the YAML strips share-based
comp; the in-code path strips depreciation only). Last session's
audit showed divergences of **100-1571% across fixtures** under that
loophole.

### Spec for the hardened gate

The hardening flips every variant to a hard threshold and forbids
threshold widening via inline source-code comment in the same shape
as the F3.16 ADR's `F-A3.1 threshold widening forbidden` lock:

```python
# scripts/check_methodology_parity.py (revised)

# ── F3.16 ADR DISCIPLINE: thresholds below are LOCKED ────────────────
# Threshold widening is explicitly forbidden. The F4.2-PARITY gate's
# whole purpose is to ensure the YAML methodology layer is a faithful
# reproduction of the in-code EBITDA values, not a separate set of
# numbers. Any divergence > 1 RON is a YAML bug; fix the YAML, do not
# widen the gate.
#
# Per-fixture exceptions are also forbidden. The discipline mirrors
# F-A3.1's locked thresholds (see docs/ADR-F3.16-closure.md §invariant
# (b)). If a new fixture genuinely needs different methodology
# behavior, ship a per-fixture methodology profile, not a per-fixture
# threshold.
# ─────────────────────────────────────────────────────────────────────
TOLERANCE_RON = 1.0
TOLERANCE_PER_VARIANT = {
    "reported": TOLERANCE_RON,
    "strict":   TOLERANCE_RON,
    "cash":     TOLERANCE_RON,  # was "info only" pre-3b.6; locked HARD now
    "adjusted": TOLERANCE_RON,
}
```

The four variants now each carry the same ±1 RON tolerance. The gate
fails on the first divergence > 1 RON on any variant on any fixture.
The "info only" code path is **deleted**, not commented out — the
discipline rule from the F3.16 ADR forbids prose comments that
document divergences (invariant (c)).

### What changes in the YAML to make the gate green

The current YAML `methodology.ebitda.cash` formula strips a different
set than in-code. Bringing them into ±1 RON parity is a YAML change:

```yaml
# src/engine/methodology/ro_v1/ebitda.yaml (revised)
ebitda:
  cash:
    description: "EBITDA adjusted for non-cash items at the cash-flow boundary."
    formula:
      - operating_revenue
      - operating_expenses     # stripped: depreciation only (same as in-code path)
      - exceptional_items      # one-time gains/losses excluded
      # share-based comp strip REMOVED — was the source of the 100-1571% divergence;
      # the in-code path doesn't have an SBC line on RO-RAS data anyway.
```

That YAML edit is the minimum surface to flip cash to HARD. The
3b.6 PR ships the YAML edit + the gate hardening + the source-code
comment lock TOGETHER so a divergent YAML can't merge without a
gate fail.

## §2 — Consumer cutover mapping

Every UI surface that displays EBITDA today reads from in-code legacy
fields. The cutover routes each surface to the canonical methodology
field. The discipline:

- **Headline values** (KPI tiles, dashboards) always read
  `methodology.ebitda.reported` — the statutory value that ties to
  the filed P&L.
- **Valuation surfaces** (EV/EBITDA, DCF inputs) read
  `methodology.ebitda.adjusted` — the value with one-offs stripped
  that the multiples are calibrated against.
- **Briefing prose** receives all four variants as input fields;
  the prompt forbids new computation but allows referencing any
  variant by name.

### Per-consumer mapping table

| Consumer surface | Current source | Target source | Behavior change |
|---|---|---|---|
| Dashboard KPI tile "EBITDA" | `assembled_pl.ebitda_statutory` | `methodology.ebitda.reported` | None (byte-identical post-F4.2 hardening). |
| P&L tab "EBITDA" row | `assembled_pl.ebitda_statutory` | `methodology.ebitda.reported` | Fixes the Carniprod **−4.37M** display bug (currently shows the reconstruction view; the methodology field surfaces the anchored value). |
| Briefing prompt headline | `assembled_pl.ebitda_statutory` | `methodology.ebitda.reported` | Prompt explicitly forbids re-computation (see §4). |
| Briefing prompt body (prose) | (free access to all PL fields) | All 4 variants exposed as named fields | Prose can reference `ebitda.strict` / `ebitda.cash` / `ebitda.adjusted` by name; not compute new values. |
| Recommendations panel | `assembled_pl.ebitda_statutory` | `methodology.ebitda.reported` | Same as Dashboard tile. |
| Risks & credit (Altman Z′, EBITDA/interest) | `assembled_pl.ebitda_statutory` | `methodology.ebitda.reported` | Same. |
| Valuation EV/EBITDA | `assembled_pl.adjusted_ebitda` | `methodology.ebitda.adjusted` | None (byte-identical). |
| Valuation DCF "EBITDA base" | `assembled_pl.adjusted_ebitda` | `methodology.ebitda.adjusted` | None. |
| Export — summary rows | `assembled_pl.ebitda_statutory` | `methodology.ebitda.reported` | Same. |
| Export — detail rows | (just ebitda_statutory) | All 4 variants in detail rows | New — gives auditors the full set. |

### Implementation pattern (per consumer)

Each consumer migrates with a tiny helper that prefers the canonical
envelope but falls back to legacy fields for the deprecation window:

```python
def ebitda_for_surface(period, variant: str = "reported") -> float:
    """Per F4.0 §3e parallel-emission discipline.

    Returns the canonical methodology value when available; falls back
    to the in-code legacy field with a deprecation warning otherwise.
    The fallback is removed in F4.7 (cutover horizon: 2026-11-23).
    """
    canonical = (period.get("assembled_canonical_v1") or {}).get("methodology") or {}
    ebitda = canonical.get("ebitda") or {}
    if variant in ebitda:
        return float(ebitda[variant])

    # Legacy fallback — `deprecated_fields` flag added to the response
    # so the FE can surface a warning toast (telemetry only; not
    # user-visible).
    legacy_map = {
        "reported": "ebitda_statutory",
        "strict":   "adjusted_ebitda",
        "cash":     "ebitda_cash",
        "adjusted": "adjusted_ebitda",
    }
    pl = (period.get("statements") or {}).get("assembled_pl") or {}
    value = pl.get(legacy_map.get(variant, "ebitda_statutory"))
    period.setdefault("deprecated_fields", []).append(f"legacy_ebitda:{variant}")
    return float(value or 0)
```

This helper is added to a new shared module and adopted incrementally
per consumer (one PR per surface or per logically-coupled batch).

## §3 — Parallel emission discipline (deprecation window)

Per F4.0 §3e — the in-code EBITDA fields stay alive as deprecated
aliases through one quarter, then get deleted in F4.7 (2026-11-23).

During the deprecation window:

1. **Both fields are written.** Every period that runs through the
   pipeline writes BOTH `assembled_pl.ebitda_statutory` AND
   `methodology.ebitda.reported`. The F4.2-PARITY gate guarantees
   they're byte-identical.
2. **API responses include `deprecated_fields`.** Every response
   shape that surfaces an EBITDA field also surfaces the
   `deprecated_fields` array listing any legacy fields the caller
   read (populated by the `ebitda_for_surface` helper above). FE
   consumers log these to internal telemetry; they do NOT
   user-surface them.
3. **Removal happens in F4.7.** The legacy fields get removed from
   the pipeline output, the helper's fallback branch gets removed,
   and any consumer still reading legacy fields surfaces a clear
   `KeyError` in the deprecation-period telemetry — that's the
   signal to fix that consumer before the F4.7 PR merges.

Per F4.0 §3e the deprecation window is **one quarter, not negotiable**.
Shorter horizons risk a consumer not being migrated; longer
horizons risk the methodology layer drifting from in-code without
being noticed.

## §4 — Briefing prompt discipline (the Carniprod −6.87M problem)

The Carniprod briefing-prose problem: in the post-3b.2 deploy, the
LLM-generated briefing referenced "EBITDA of −6.87M" — a number that
appears NOWHERE in the canonical or in-code fields. The LLM was
computing a new EBITDA in prose by combining other input fields,
producing a value the engine had not validated.

### Fix — single-line briefing prompt addition

The briefing prompt template (`src/engine/api/pipeline.py::stage_narrate`,
the `STAGE_NARRATE_SYSTEM_PROMPT` constant) gets one new line in the
"facts you may reference" section:

```
EBITDA RULE — EBITDA values referenced in the briefing MUST come from
the canonical fields in the input dict. Specifically: use
`methodology.ebitda.reported` for headline statements,
`methodology.ebitda.strict` / `cash` / `adjusted` when comparing
methodologies by name. DO NOT compute new EBITDA values in prose.
Do NOT sum or transform PL line items to produce a different EBITDA.
If a methodology variant you want to reference is missing, say so
explicitly ("cash-view EBITDA was not computed for this period")
rather than approximating.
```

The "do NOT compute" instruction is the binding constraint. Modern
LLMs respect explicit DO-NOT instructions well; the prior briefing's
−6.87M was the LLM treating "free reasoning over input fields" as
permission to do arithmetic. The new wording removes that
permission.

### Verification

The briefing prompt change is a string-literal edit. Verification is
manual: re-generate the Carniprod briefing post-cutover, confirm the
EBITDA value in the prose matches `methodology.ebitda.reported`
exactly (or `methodology.ebitda.adjusted` if the prose explicitly
references the adjusted view).

There is no automated gate on briefing prose — LLM output is
inherently variable. Instead, the gate is on the **input dict**: if
`methodology.ebitda.reported` is the same byte-for-byte across deploys
(which the F4.2 hardening guarantees), and the prompt forbids
recomputation, the briefing's headline EBITDA is reproducible.

## §5 — Methodology version provenance

Per F4.0 §7 detection envelope: every API response that surfaces an
EBITDA value must include the `methodology_version` field. This is
the audit trail letting the operator trace any displayed number back
to the methodology spec that produced it.

### What's already wired

`F4.1e` (shipped) added `financial_periods.methodology_version` as a
persisted column, populated by `stage_assemble` at write time.

`F4.3` (shipped) added the detection envelope including
`methodology_version` to every period detail API response.

### What 3b.6 verifies

3b.6 doesn't add new wiring here; it verifies the existing wiring is
exercised on every EBITDA-bearing surface. Specifically:

- Dashboard period detail endpoint: response carries
  `meta.methodology_version` (verify with `curl | jq '.meta.methodology_version'`).
- Briefing endpoint: response carries `meta.methodology_version` AND
  the briefing prompt was generated against that version (the prompt
  includes the version as a system-prompt input).
- Export PDF: footer reads "Methodology: `{methodology_version}`"
  near the source attribution line.

A single failing surface here is a 3b.6 ship blocker.

## §6 — Resolution for the 3b.5 open questions

The 3b.5 plan doc (`docs/F3.16-3b5-backfill-plan.md`) surfaced three
open questions. 3b.6 resolves them:

### Q1: Why do EEI/Sibiu PDFs land only 60-200 line_items vs Scandia xlsx's 644-653?

**Resolution:** Defer to `[F3.18-PDF-LINE-ITEM-COUNT]`. The
suspicion (Claude over-summarizing on the PDF path) is testable but
out of 3b.5/3b.6 scope. The 3b.5 backfill produces a fresh envelope
regardless of line_item count; coverage is met. 3b.6 cutover reads
methodology fields from the envelope, not the line_items table, so
the PDF-vs-xlsx asymmetry doesn't affect any user-visible value.

`[F3.18-PDF-LINE-ITEM-COUNT]` ticket scope:
- Re-extract one EEI PDF + one Sibiu PDF with verbose logging on
  the Claude pipeline.
- Compare line_items count + content against the Scandia xlsx
  baseline for similar-size companies.
- If Claude is over-summarizing, prompt-tune to preserve full
  account lists.

### Q2: Does the re-extract produce different line_items than today (downstream re-firing)?

**Resolution:** The 3b.5 orchestrator's per-period diff catches this
at the user-visible field layer (total_assets / current_year_pnl).
If the diff is within tolerance, downstream consumers (briefings,
alerts, recommendations) see the same headline values they did
before. Some MAY re-fire because the period's `updated_at` changes
— that's expected and acceptable per the plan's rollback decision
tree.

Defer deeper investigation to `[F3.18-DOWNSTREAM-REFIRING]` if any
specific consumer surfaces a bug post-backfill. Don't pre-emptively
build instrumentation for a hypothetical problem.

### Q3: Multi-period org chronology

**Resolution:** The 3b.5 orchestrator processes periods in
`TARGET_PERIODS_BY_PREFIX` order (smallest line_items first). The
operator's runbook (Step 4 / Step 5 in
`docs/F3.16-3b5-EXECUTION-HANDOFF.md`) does NOT explicitly order
by organization or chronology. Reconsider this in the rollback
decision tree if a multi-period org surfaces a cross-period
briefing inconsistency.

Predicted behavior: of the 8 target periods, the chronological
spread is FY2019 (Sibiu × 2) + FY2025 (everything else). FY2019 is
isolated org-wise from FY2025 in the prod data set — no cross-period
briefing should reference both.

If post-backfill a cross-period briefing does surface a 2019/2025
inconsistency, the fix is a re-trigger on the more recent period in
that org so the briefing regenerates with both periods' fresh
envelopes. Document this in the closure record if it happens.
